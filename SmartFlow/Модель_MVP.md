# SmartFlow: модель минимального продукта

## Цель
Проверить, помогает ли единый сценарий «загрузить → проверить → согласовать → выгрузить» уменьшить ручную работу со счетами поставщиков небольшой сервисной компании. Это конкретизация исходной идеи автоматизации документов, а не реализация всей платформы из исходной презентации.

## Пользователи и процесс
Оператор загружает счёт и проверяет пять полей: номер, дату, поставщика, ИНН и сумму в рублях. Система выбирает согласующего по настраиваемому порогу. Бухгалтер согласует небольшие суммы; руководитель — суммы выше порога. Согласующий может вернуть документ с причиной. После исправления оператор отправляет его повторно. Все действия фиксируются в истории. Реестр выгружается в CSV.

В текущей сборке роли демонстрируются в одном интерфейсе; отдельные пользователи и авторизация не реализованы.

## Реализованные истории пользователя

| Потребность | Реализация | Как проверить |
|---|---|---|
| Не переносить все реквизиты вручную | Извлечение из TXT, DOCX, PDF с текстом по правилам | Загрузить файлы из examples |
| Исправить ошибку распознавания | Редактирование пяти полей и проверка обязательных значений | Изменить поставщика, сохранить |
| Настроить простой маршрут | Порог суммы без изменения кода | Сравнить счета 24 500 и 85 000 ₽ |
| Получить решение по счёту | Согласование / возврат с обязательным комментарием | Вернуть, исправить, отправить снова |
| Найти документ и понять его статус | Реестр, поиск, фильтр и история | Поиск по «Вектор», фильтр «Согласован» |
| Перенести результат в таблицу | CSV всего реестра | Открыть экспорт в Excel, кодировка UTF-8, разделитель «;» |
| Продолжить работу позже | SQLite на локальном диске | Перезапустить сервер |

## Модель данных

**Document:** id, имя файла, SHA-256 содержимого, извлечённый текст, реквизиты, статус, согласующий, время создания.

**Event:** id, ссылка на документ, время события, описание действия.

**Settings:** порог согласования; начальное значение 50 000 ₽.

Исходные бинарные документы не архивируются. Статусы и маршрут изменяются на сервере; история пополняется при действиях пользователя. Проверка SHA-256 обнаруживает только идентичные файлы, а не один и тот же счёт в разных форматах.

## Границы MVP
Сканы без текстового слоя отклоняются. Нет OCR, ML, электронной подписи, интеграций с 1С и мессенджерами, платежей, многопользовательских ролей и рассылок. Проверка реквизитов человеком обязательна. Чтение по правилам рассчитано на явно подписанные поля; точность на произвольных счетах не измерена.

## Проверка гипотезы
Предлагаемый пилот: 3 пользователя и 30–50 обезличенных счетов из реального потока. До пилота проверить форматы, правила доступа и возможность использования документов. Для одинаковых счетов измерить полное время ручной обработки и работы через MVP. Зафиксировать исправления каждого поля и ошибки маршрута.

Основной критерий гипотезы: снижение медианного времени минимум на 30% при обязательной проверке реквизитов. Дополнительные показатели: доля исправленных полей, число необработанных форматов, успешность завершения сценария без помощи. Это план проверки, а не результаты состоявшегося пилота.

## Следующая версия
Если сценарий полезен: авторизация и роли, хранение оригиналов и резервное копирование; затем OCR для наиболее частых сканов и одна востребованная интеграция. Решение об ML принимать по ошибкам и объёму ручных исправлений. Цена подписки и бюджет развития требуют отдельной проверки; финансовые обещания исходной презентации не переносятся как подтверждённые показатели.
